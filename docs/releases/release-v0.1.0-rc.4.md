# ops-agent v0.1.0-rc.4 发布：审查修复与恢复链路加固

> 2026-11-09（北京时间） · 上一版：[v0.1.0-rc.3](release-v0.1.0-rc.3.md) · [GitHub Release](https://github.com/mengbin92/ops-agent/releases/tag/v0.1.0-rc.4)

v0.1.0-rc.4 是第四个**候选发布版本（prerelease）**，交付本轮代码审查及复审确认的
授权、敏感读取、远程文件恢复、通知送达与日志采集修复，不增加产品能力或主内核运行依赖。

**版本判定：PATCH 级修复，继续候选序列。** 按[下一阶段规划](../plans/2026-10-25-next-stage.md)
的候选期规则，保持 `0.1.0` 基线并递增为 `0.1.0-rc.4`，不升 MINOR，也不提前发布正式 `0.1.0`。
S3 的真实 SSH 恢复、断线 `unknown` 防重放、服务后验仍缺实机通过证据，S4 正式发布门禁尚未完成，
当前 R2 观察也未完成全部七天。本地回归通过不能替代这些外部验收。

## 发布内容

### 1. A2A 授权身份与只读模式（R01、R02、F01、F02）

**根因**：续跑确认仅把用户答复交给第一个问题，未完整绑定上一张变更单；只关闭确认回调不能阻止
已有审批戳被写工具消费。复审还发现展示文本遗漏环境字段，以及普通澄清中断保留旧审批身份。

**修复**：确认按工具、完整参数及实际环境的稳定身份匹配，覆盖 `kubeconfig`、SSH identity/options、
快照声明和次数；确认框展示相关环境与快照内容。普通问题会使旧审批失效，task 分槽和一次答复仅确认
一单的限制保留。A2A `--read-only` 复用无人值守只读工具集，在 schema 与 dispatch 两层拒绝写操作，
即使已有合法戳也不能执行。

**影响入口**：A2A 服务、`ops_approve`、`scenario_run` 及其确认通道。REPL 等直接确认入口继续复用同一工具实现，
单发非交互模式的人工预授权不被一并禁止。

### 2. 认证请求与远程文件恢复（R03–R06、F03）

**根因**：默认 HTTP 重定向可能把认证头带到另一端点；远程快照仅检查输入路径，直接保存 stdout 会混入
登录噪声；固定标记可能与文件正文碰撞，`cat` 失败也可能被末尾 `printf` 覆盖成成功。回滚预览缺少实际恢复
入口已有的路径改向检查，敏感内容可能先进入确认前的 diff。

**修复**：模型请求和 `doctor` 探活不再跟随重定向。快照在解析后复查真实路径的敏感门禁，统一使用随机标记的
字节读取协议并保留调用方时间预算，读取失败立即中止。回滚预览先固定目标配置、解析并核对真实路径、复查敏感
路径，最后才读取内容，末级或父目录软链接改向均在输出前拒绝。

**影响入口**：两种模型协议与 `doctor`；远程快照、回滚预览、回滚前副本；CLI、Agent 和 MCP 的对应入口。

### 3. SMTP 部分送达与心跳恢复（R07、R08、F04、F05、V01）

**根因**：SMTP 部分收件人拒收不会必然抛异常，原实现可能误记整条成功；首次或重试中的部分成功受众未完整
传入恢复状态机，会让已收到异常的人漏收恢复。常驻调度仅启动时检查心跳，补修中的临时旗标又可能在写盘失败时
过早清除恢复意图。

**修复**：通知记录保存已接受收件人的散列，部分失败仍记 `failed`，只补发未成功者；部分重试新增的受众也会同步
到状态机。只有全部投递完成才清恢复态和记录完成事件；纯恢复消息的部分失败不会把原异常受众反向缩小。
移除心跳恢复旗标，每次成功扫描后由通知状态机判断恢复与去重，首次心跳写盘失败后下一轮仍能补上恢复。

**已确认的边界**：

- **纯恢复**消息按收到过原异常的受众收窄；同轮有新异常和恢复的 **mixed** 消息继续聚合为一条，发给全部收件人，
  恢复行也随之可见。这是保证新异常送达、避免拆分消息刷屏的既有取舍。
- 常驻循环**每轮调用一次通知状态机**，增加同量级的通知状态读写，以保留写盘失败后的恢复机会；不再用额外旗标
  省略该检查。

**影响入口**：调度自动通知、`notify retry`、SMTP 发件箱与异常恢复状态；常驻 daemon 和 `schedule run --once`。

### 4. 日志采集与验收文档（R09）

**根因 → 修复**：本机日志采集仅保留 stdout，可能丢掉容器写到 stderr 的错误日志；现在合并两路输出，非零退出
明确作为采集失败。发布前机器评审进一步发现远程分支仍将“非零退出且有错误输出”当成日志，现已在共享远程
采集函数中一并拒绝，诊断摘要先脱敏，不把命令错误或不完整输出当成成功采集。

**影响入口**：本机与远程 Docker/journal 日志来源及其 `logscan` 工具调用。

本版同时收录 R1/R2 观察状态回填及独立通知演练记录。11月9日通知演练使用隔离状态目录，不能作为 R2 观察期内
通知送达或本版实机验收的替代证据；原始 R1 记录和历次发布结论保留。

## 兼容性与升级注意

- 主内核仍为 Python 3.9+、纯标准库，无新增运行依赖；A2A 仍使用独立的可选依赖及其 Python 版本要求。
- A2A 写确认会更严格：重启服务后内存中的待确认单不会保留，调用方须重新发起并确认；请求或实际环境变化也须
  重新确认。普通澄清的答复不能代替写操作批准。
- 本次没有执行状态迁移，也没有自动撤销用户状态目录内全部审批戳。升级前应结束在途变更、核对并撤销不再需要的
  旧授权；不要把旧确认答复或恢复副本中的审批戳重新当作授权使用。
- 模型端点若依赖重定向，现在会明确失败，需人工核对上游供应商给出的最终端点；不会继续转发认证头。
- 敏感真实路径和快照后改向的路径会更早被拒绝，不能为恢复而关闭门禁；先人工核对真实目标和可信备份。
- 新通知字段用于收件人送达事实，已有 webhook、SMTP 配置仍沿用现有格式。旧通知记录没有收件人粒度事实时，
  不能反推当时每位收件人是否实收，需保留原始证据并人工核对。

## 安装升级与回退

发布源码包与部署升级是两项操作：**本次发布不修改生产托管、当前版本指向或 R2 观察环境**。
需要部署时另按实际环境执行以下步骤，不直接覆盖运行中的代码或状态。

1. 记录当前版本和状态目录，停止全部调度、Agent、MCP/CLI 及其他状态写入者，核实在途变更和 `unknown` 记录。
   未核实的变更不能自动重放。
2. 按[状态备份与安全恢复](../ops/state-backup-recovery.md)创建并校验离线私有备份；备份含原始凭据和快照，
   不应上传到公开仓库或发布资产。
3. 下载本版源码包及 `SHA256SUMS`，校验后解包到新的版本目录，保留旧版本。Git 安装可在停写后的干净检出中使用：

   ```sh
   git fetch origin --tags
   git switch --detach v0.1.0-rc.4
   ./opsx selftest
   python3 -m unittest discover -s tests -p 'test_*.py'
   ```

4. 在**全新、独立的状态目录**恢复备份副本并检查。恢复会隔离审批、暂停 schedule/通知，将未结束执行转为需核实状态，
   不会覆盖原状态；按原有流程核对目标、执行记录、通知待发送项后，才显式启用需要的任务。无需在升级时重填凭据。
5. 切换部署指向和 `OPSX_STATE_DIR` 后先做只读检查，核对版本、心跳、报告与权限。真实变更、通知投递和故障注入
   继续按实际授权范围执行，不能因升级说明中列有步骤便自动操作生产目标。

本版修改通知状态机和调度恢复行为，属于既定规则中的运行行为重大修复。**实际部署后应固定新候选基线并重新计满
七天观察**；当前仍运行 rc.3 的 R2 不能直接证明 rc.4 已通过，也不能在尚未部署时声称新观察已经启动。

如需回退，先停止全部写入者，保留本版运行后状态和证据，切回保存的旧源码目录；需要恢复旧状态时，从部署前可信
备份恢复到另一个全新目录并人工核对。不要让不同版本并发写同一状态目录，也不要把旧状态直接覆盖到活跃目录。
代码或 Agent 状态回退**不撤销已经执行的业务命令**；文件恢复仍须按快照回滚确认并做服务后验，`unknown` 必须先核实。
旧版本包含本次修复的缺陷，回退后不应继续使用受影响能力扩大风险。
