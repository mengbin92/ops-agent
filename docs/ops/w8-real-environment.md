# W8 测试环境验收

本机可重复演练入口为 `python3 scripts/w8_acceptance.py --output <证据.json>`。
它运行真实本地进程、文件与回环 HTTP，但 LLM/通知是本地桩，不能替代本文件的外部验收。
`--require-external` 会在外部门禁未完成时退出 2，防止把本地通过误作完整发布通过。

## 需要准备的环境

- 已注册的专用 SSH 测试 target，以及允许创建、修改和恢复的绝对目录。
- 可中断的测试服务；配置恢复后还应能验证实际服务响应。
- 通过环境变量配置的测试 LLM 端点、模型与凭据。
- 专用测试 webhook 及允许接收测试告警的受众；渠道由环境负责人接入。
- 修复版本连续运行 7 天的记录；重大修复后重新计时。

当前环境检查没有发现 SSH 注册目标或 LLM 凭据。以下步骤为待执行验收清单，不能预先勾选。
所有命令在专用测试状态目录中运行；先检查 `OPSX_STATE_DIR`，不要复用生产审批、排期或通知配置。

## 实机执行顺序

1. 记录代码版本和工作树状态、主机/系统、target 的实际端点、测试服务及允许目录。
   用 `opsx targets` 核对目标，运行 `opsagent doctor`；证据不保存密钥或原始 webhook URL。
2. 用已配置测试 LLM 执行 `opsagent -p '只回复验收连通性通过，不调用任何工具'`。
   保存退出码、provider/model、时间和回复，明确这是实际 provider。
3. 对测试 target 执行 `opsx exec 'uname -s' --target <test-target>`，记录执行 id 和 SSH 实际输出。
   连通性失败时停止，不能用桩替代并标通过。
4. 在允许目录内准备带已知内容、属主/组和权限的测试配置与新配置。
   对完整复制命令先执行 `opsx revoke '<完整命令>' --target <test-target>`，再调用
   `opsx exec '<完整命令>' --target <test-target> --snapshot-file <配置绝对路径>`。
   预期拒绝且文件内容和权限不变；这一步必须先于授权。
5. 核对目标、命令、影响文件和恢复方法后，用 `opsx approve '<完整命令>' --target <test-target>`
   授权，再调用相同 `opsx exec`。保留快照 id、execution_id 和前后内容摘要。
   对服务重启/reload 单独使用已支持的 `scenario run`，保留预检与后验，不能仅以 exit=0 判服务健康。
6. 制造测试服务不健康但变更命令 exit=0 的情况，验收 `verify_failed` 与退出 7。
   失败注入必须局限于专用服务；停止条件为目标/目录不符、快照不完整、未知状态或影响超出测试范围。
7. `opsx rollback <snapshot-id>` 先看实际目标、差异和文件清单；未确认时验证无修改。
   核对后 `opsx rollback <snapshot-id> --yes`，检查配置内容、mode、属主/组及回滚前副本。
   恢复配置后需要 restart/reload 时，重新批准相应命令，再独立验证实际业务响应。
8. 在测试 SSH 会话中人为断线/超时，确认执行记录为 unknown，相同命令被拒绝重放。
   人工核实主机结果后才用 `opsx executions resolve` 记录观察结果；不能为了继续演练直接清状态。
9. 在专用通知渠道验证首次异常、持续异常去重、升级、恢复；模拟不可达并确认发件箱失败和退避补发。
   对实际 LLM 临时错误、鉴权失败、预算耗尽分别确认运行失败可见，规则检查和规则异常上报继续。
10. 按 [状态备份恢复流程](state-backup-recovery.md) 停写、备份、校验并恢复到全新目录。
    核对原始快照可用、审批需重新授权、running 不复活、排期与通知默认停用，再决定启用哪些项目。
